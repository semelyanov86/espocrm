# AGENTS.md — правила проекта миграции Vtiger 7.1 → EspoCRM

Этот файл читает каждый агент/сессия **до** начала работы. Затем — `TASKS.md` и относящиеся к этапу файлы `docs/migration/`.

## Цель

Перенести CRM `serv.itvolga.com` (Vtiger 7.1.0 + SalesPlatform SP01 + расширения VTE/ITS4You) на EspoCRM **без платных расширений** (Sales Pack, Advanced Pack, VoIP Integration и т. п.). Финансовые документы (Quote, SalesOrder, Invoice, Act, Payment), печатные формы и телефония реализуются собственным открытым кодом в этом репозитории.

## Этапность

- Работа идёт по этапам из `TASKS.md`: **один этап за сессию**. Не переходить к следующему этапу в той же сессии.
- Если этап заблокирован — сделать всю независимую работу, записать блокер в `TASKS.md`, закоммитить и остановиться.
- Каждая сессия заканчивается: обновлением `TASKS.md` и затронутых `docs/migration/*`, проверкой `git diff` и секретов (`scripts/check-secrets.sh`), отдельным коммитом, SHA в итоговом ответе.
- При расхождении документов и живого сервера приоритет у **свежей read-only проверки**; карту исправить и указать дату проверки.

## Production

- Рабочий сервер `sergey@serv.sergeyem.ru` и локальный репозиторий `/data/server` (Ansible) — **только чтение** до этапа 10 (размещение рядом с Vtiger) и 11 (переключение), каждый требует отдельного явного разрешения пользователя.
- Разрешено на сервере: `SELECT` в сессии `SET SESSION TRANSACTION READ ONLY`, `ls/stat/find/wc/du`, `asterisk -rx "... show ..."`, чтение логов для агрегатов. Запрещено: любые записи в БД/файлы, рестарты сервисов (Asterisk, Apache, php74-fpm, MySQL), изменения cron, установка пакетов.
- Код Vtiger/SalesPlatform анализируется по локальной приватной копии `/data/itvolga/espo-private/vtiger-src/vtiger7/` (`scripts/audit/sync-vtiger-src.sh`: только код, без данных, секретов и закрытых модулей VTE/ITS4You); на сервере — только данные (read-only SQL) и адресные проверки.
- Скрипты для сервера передаются **inline** (`scripts/audit/lib.sh`: `remote_sql_py`, `remote_py` — base64 в `python3 -c`, shell — через `bash -s`); файлы на сервере не создаются. Если временный файл неизбежен — `mktemp` + `trap rm` в одной SSH-команде.
- Не перезапускать production Asterisk и не менять транки/маршрутизацию. AMI — только локальный, минимальные права.
- Сохранять PHP 7.4 / контейнер `php74-fpm`: им пользуется Lahic.
- Старые `scripts/export-vtiger.sh`, `task export:vtiger`, `task migrate:vtiger` из `/data/server` относятся к прежнему серверу — не использовать как готовый экспорт.

## Данные и приватность

- В Git **не попадают**: дампы БД, выгрузки строк, вложения, аудио (WAV), персональные данные, реквизиты доступа, реальные реквизиты организаций и клиентов, приватные отчёты сверки.
- Приватные результаты — вне репозитория: `/data/itvolga/espo-private/` (права `700`). В Git — только код, шаблоны конфигов, обезличенные сводки (счётчики, схемы, распределения значений справочников).
- **Поля доступа контактов** (`Contacts.cf_1322` AnyDesk ID, `cf_1324` AnyDesk Password, `cf_1326` Hostname, `cf_1328` IP) и их история в `vtiger_modtracker_detail`: значения **никогда** не выводить в консоль, логи, отчёты, тесты, фикстуры. Только счётчики и хеши, вычисленные на сервере.
- Имена людей, телефоны, e-mail, ИНН/счета, IP клиентов в документах заменяются на `user#<id>`, счётчики или шаблоны (`С-999`).
- Запросы для доказательств — в `scripts/audit/sql/*.sql` или `docs/migration/evidence.md`: воспроизводимые, без значений строк и без секретов.
- Секреты (пароли БД, AMI, API-ключи) — только вне Git (vault/`.env` вне репозитория); в Git — шаблоны `*.example`. Секреты стенда — `/data/itvolga/espo-private/stand/local.env`, backup стенда — `/data/itvolga/espo-private/stand/backups/` (содержат `config-internal.php`).
- Тестовые данные — только синтетические: фикстуры в `tests/fixtures/synthetic/`, тесты создают и удаляют свои записи сами (`tests/stage03/`); JSON вне `custom/Espo/{Custom,Modules}/`, `client/custom/` и этого каталога игнорируется `.gitignore`.

## Код и структура

- `scripts/audit/` — воспроизводимый аудит источника (`run-audit.sh`).
- `docs/migration/` — постоянная память миграции (карта полей, связи, решения, вопросы, доказательства).
- Локальный стенд (этап 02, `docs/local-stand.md`): ядро EspoCRM распаковывается в корень репозитория из закреплённого релиза и в Git не попадает; настройки — `deploy/local/stand.conf`, шаблоны — `deploy/local/templates/`, скрипты — `scripts/stand/`, команды — `Taskfile.yml`. Консоль EspoCRM — только `task espo -- …` (от пользователя `espocrm`, PHP 8.5), не `bin/command` напрямую. Ядро не править: изменения — только в `custom/`, `client/custom/`.
- Модель CRM (этап 03, D-40): модуль `custom/Espo/Modules/Itvolga` (метаданные, layouts, i18n, хуки, API, команда `itvolga-setup-acl`) и `client/custom/modules/itvolga`; `custom/Espo/Custom` — только для правок администратора. Описание — `docs/migration/model.md`; развёртывание — `task model:apply`, тесты — `task test:stage03`, сверка с картой — `task model:check`. Словарь значений (`metadata/vtigerValueMap`) и опции enum не править вручную: генератор `scripts/model/build_value_maps.py`.
- Финансы (этап 04.1, D-45): контракт сущностей — `docs/migration/finance-contract.md` §11; расчётное ядро без зависимостей от EspoCRM — `custom/Espo/Modules/Itvolga/Tools/Finance/` (bcmath, float запрещён, исходные суммы не пересчитываются); тесты — `task test:finance` (приватная часть — по срезу аудита, печатает только счётчики), профиль источника — `task finance:profile -- <срез>`. Правила, которых нет в данных и нет в решениях (D-47, D-49), ядро отклоняет, а не угадывает.
- Финансовые документы (этап 04.2, D-50…D-56): позиции правятся только через документ (поле `itemList`, одна транзакция, `Tools/FinanceDocument/`); новый документ — запись в реестр `metadata/app/itvolgaFinance.json`; правило правки импортированных документов — `Tools/Finance/Editing/DocumentEditor` (`finance-contract.md` §14); юрлицо и счётчики номеров — `task espo -- itvolga-setup-finance` (входит в `task model:apply`); тесты — `task test:stage04`.
- Счета (этап 04.3, D-57…D-61): `Invoice`/`InvoiceItem` — тот же путь (запись в реестре, номера `С-N`); контроль итогов всех документов — «Пересчёт ядра» (`expected*`, `Tools/FinanceDocument/SourceMarks`, пишет `itvolga-finance-verify`) и «Итоги Vtiger» (`source*`, один раз при первом пересчёте); исходное `spcompany` импорта хранится в `vtigerData.spcompany` и разрешается `LegalEntityResolver` при каждом сохранении с `SaveOption::IMPORT` (`finance-contract.md` §15).
- Платежи (этап 04.4, D-62…D-68): `Payment`/`PaymentAllocation` — реестр `payments` в `itvolgaFinance.json`; распределения правятся только таблицей платежа (`allocationList`, `Tools/FinancePayment/`), оплата хранится у счёта и заказа и пересчитывается под «журналом» (`finance-contract.md` §16, D-64); ремонт — `task espo -- itvolga-finance-settle`. Импорт любых финансовых записей — ORM с `SaveOption::IMPORT` **и** `SaveOption::SILENT` (без `SILENT` запись отклоняется); удалённые распределения и их владельцы не восстанавливаются.
- Акты (этап 04.5, D-69…D-71): `Act`/`ActItem` — тот же путь документов (реестр, номер без префикса с 403); связь `Invoice.act` ↔ `Act.invoices` без ограничения 1:1 (несколько счетов — полем «Акт» счёта); «Создать акт» — обратная конвертация реестра: ссылка пишется в счёт заглушкой ядра `invoicesIds`, счёт с живым актом второй акт не получает (`ConversionSourceGuard`, проверка и при сохранении под блокировкой счёта); связи акта с платежами нет (`finance-contract.md` §17). Блокирующие чтения финансовых записей — только через `Tools/FinanceDocument/RowLock` (собственная строка, без JOIN имён связей; D-72).
- Сквозной сценарий (этап 04.6, D-73…D-76): конвертации копируют и команды источника (поля linkMultiple загружаются); номер сохранённого документа или платежа меняет только импорт (`Hooks/Common/FinanceNumberGuard`); смена статуса или типа платежа и его удаление требуют права чтения каждого его документа; панели документов — навигация (без «Выбрать»/«Отвязать», дочерние документы — только просмотр). Покрытие всех финансовых полей и связей аудита — генерируемый `docs/migration/finance-coverage.md` (`task finance:coverage`, свежесть — `task model:check`); статуса карт `контракт` нет; тесты цепочки — `tests/stage04/test_stage04_6.py`. Документ с панели сделки получает её контрагента и контакт, адреса документа — копия адресов контрагента при создании с панели (`handlers/finance/account-address`) и при выборе контрагента в форме (вид поля `views/finance/fields/account`: адреса приходят с выбранной записью, без своего запроса; D-179).
- Печатные формы (этап 05, D-79…D-83): счёт, акт, ПКО (только приходы), КП и заказ — код модуля, не записи `Template`: реестр `printForms` в `itvolgaFinance.json`, HTML/CSS — `Resources/printForms/`, кнопка «Печать» → `?entryPoint=itvolgaPrint` → `Tools/FinancePrint/PrintService` (доступ к записи, контрагенту и юрлицу; чтение в одной транзакции; печать ничего не пишет) → чистый `Tools/Finance/Printing/Presenter` (суммы — хранимые, только `Decimal`, сумма прописью — `AmountInWords`) → Dompdf ядра через `Builder`. Шрифт — Liberation Sans в `Resources/fonts/` (после развёртывания — clear-cache). Реквизиты продавца — только из `LegalEntity` (в Git и фикстурах — синтетические). Тесты — `task test:stage05` (PDF через `pdftotext`/`pdfinfo`/`pdffonts`/`pdfimages`), фикстура и PDF для просмотра — `tests/stage05/ui_fixture.py create|render|delete`.

Тесты — `task test:reports`, `task test:stage05.3` (уборка писем и файлов — `tests/stage05_3/mail_fixture.php`); UI-фикстура — `tests/stage05_3/ui_fixture.py create|delete`.

Метод не снимать из «Доступных методов 2FA», пока им пользуются (ядро пропустит второй фактор). Контракт — `docs/migration/security-key.md`; тесты — `task test:security-key`, `task test:security-key-stand`; UI-фикстура — `tests/security_key_stand/ui_fixture.py create|delete`.
- Защищённый снимок источника (этап 06.1, D-133…D-138): `scripts/snapshot/` (Python, только стандартная библиотека). Базы `vtiger7` и `asteriskcdrdb` выгружаются одной сессией `READ ONLY` с `CONSISTENT SNAPSHOT`: строки — hex-кодеком, число строк, дайджест и счётчики колонок сервер считает в той же транзакции. Файлы — опись с sha256 на сервере (inline) и `rsync` по списку. Снимок полный, секреты и история полей доступа не заменяются (D-133); лежит в `/data/itvolga/espo-private/snapshots/<id>/` (700/600), публикуется переименованием, удаляется только `task snapshot:delete -- <id> --yes`. Проверка: восстановление во временную базу стенда (точное имя, `sql_log_bin=0`, удаляется) и пересборка карт аудитом по копии. Формат и границы — `docs/migration/snapshot.md`, протокол — `snapshot-protocol.md` (`task snapshot:protocol`), тест кодека — `task test:snapshot`. Импорт читает только проверенный снимок; кодек не расширять без теста туда-обратно.
- Импорт базовых сущностей (этап 06.2, D-139…D-146): `scripts/import/` (Python: спецификация правил `spec.py` — колонка за колонкой против `field-map.csv`/`relations.csv`, чтение проверенного снимка `source.py` через `verify.restored_databases`, сверка `importer.py`) + универсальный писатель `task espo -- itvolga-import` (`Tools/Import/`): значения — только в stdin процесса PHP, ответы — строки с меткой, тексты исключений не выводятся. Ключ — `vtigerId` с удалёнными; источник побеждает, неизменённое не пишется, ручные связи с записями EspoCRM остаются (с 06.4 связи между импортированными записями и исчезнувшее из источника — по источнику); ссылки на модули следующих этапов ждут их (повторный запуск достраивает). Запуск — `task import:run -- --snapshot <id>` (backup стенда первым), сводка — `task import:summary -- <прогон>`, тесты — `task test:stage06.2` (синтетика, ключи ≥ 900 000 000, уборка по записанным id). Отчёт по записям и колонкам — `/data/itvolga/espo-private/import/<прогон>/`, в Git — только `import-summary.md` и `import-columns.md` (с этапа 08). Новую сущность импорта — правилами в `spec.py` (покрытие карт проверяется до чтения), не правкой писателя. Контракт — `docs/migration/import.md`.
