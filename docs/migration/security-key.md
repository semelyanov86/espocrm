# Ключ безопасности (YubiKey) — второй фактор WebAuthn

Вне этапов, 2026-10-06, запрос владельца. Решения — D-128…D-132 (`decisions.md`). Код — модуль `Itvolga`, ядро EspoCRM
10.0.9 не правится.

## 1. Что сделано

В «Администрирование → Аутентификация → Доступные методы 2FA» появился метод «Ключ безопасности (YubiKey)»
(ключ метода `ItvolgaSecurityKey`). Пользователь включает его штатной кнопкой «Безопасность» в своей карточке, а при
обязательной 2FA (`auth2FAForced`) — в окне ядра после входа. Он регистрирует один или несколько ключей (основной и
запасной) и потом входит паролем и касанием ключа.

- Технология — WebAuthn / FIDO2: подходит любой FIDO2-аутентификатор (YubiKey 5, Security Key, другие ключи; браузер
  может предложить и Windows Hello или телефон). Производитель не проверяется (`attestation: "none"`).
- Нужно касание ключа (флаг UP); PIN или отпечаток не требуются (`userVerification: "discouraged"`): пароль уже
  первый фактор.
- Алгоритмы: ES256 (по умолчанию у YubiKey), EdDSA (Ed25519, расширение sodium), RS256.
- Второй шаг входа (и ключ, и коды TOTP/e-mail/SMS ядра) — в рамке фирменной страницы входа (D-127).

## 2. Как устроено

| Часть | Где | Что делает |
|---|---|---|
| Реестр метода | `Resources/metadata/app/authentication2FAMethods.json` | `ItvolgaSecurityKey`: окно настройки, классы входа и настройки |
| Чистое ядро | `Tools/SecurityKey/Core/` | разбор и проверка: base64url, подмножество CBOR, authenticatorData, COSE → SPKI, подписи (openssl, sodium), clientDataJSON, счётчик; без зависимостей от EspoCRM |
| Вход | `Tools/SecurityKey/SecurityKeyLogin.php` | `TwoFactor\Login` ядра: первый запрос — вызов и параметры для браузера; второй — гашение вызова и проверка ответа ключа |
| Настройка | `Tools/SecurityKey/SecurityKeyUserSetup.php` | `TwoFactor\UserSetup` ядра: `getData` — параметры регистрации с вызовом настройки; `verifyData` — проверка 1–5 ключей и замена набора |
| Вызовы | `Tools/SecurityKey/Challenges.php` | одноразовые вызовы в штатной `TwoFactorCode` |
| Ключи | `Tools/SecurityKey/Credentials.php` | список ключей в `UserData.cSecurityKeys` (JSON) |
| RP | `Tools/SecurityKey/RelyingPartyProvider.php` | RP ID и origin из `siteUrl` |
| Хук | `Hooks/UserData/ClearSecurityKeys.php` | стирает ключи, когда пользователь уходит с метода |
| Клиент | `client/custom/modules/itvolga/src/` | `views/login.js` (направляет второй шаг), `views/login/brand.js` (панель бренда), `views/login-second-step.js` (коды ядра), `views/login-security-key.js` (шаг ключа), `views/user-security/modals/security-key.js` (окно настройки), `security-key.js` (WebAuthn в браузере), `login-response.js` (исправление ядра, §6) |

Нового API нет: настройка идёт штатным путём `UserSecurity`, вход — штатным `GET App/user`.

### Вход

1. Браузер отправляет имя и пароль (`GET App/user`). Ядро проверяет пароль и вызывает `SecurityKeyLogin`.
2. Без заголовка `Espo-Authorization-Code` метод выдаёт вызов: 32 случайных байта, срок 5 минут, прежний вызов
   пользователя гасится — под блокировкой строки `UserData`, поэтому после одновременных первых шагов жив один вызов. Ответ ядра — 401, `X-Status-Reason: second-step-required` и тело:
   `{"message": "itvolgaSecurityKeyTouch", "view": "itvolga:views/login-security-key", "data": {"state": "ready",
   "publicKey": {"challenge", "rpId", "timeout": 120000, "userVerification": "discouraged", "allowCredentials":
   [{"type": "public-key", "id", "transports"}]}}}`.
3. Шаг ключа сразу просит браузер о касании (кнопка «Подтвердить ключом» — повтор и запасной путь для Safari). Ответ
   ключа уходит повторным `GET App/user` с теми же учётными данными и заголовком `Espo-Authorization-Code`:
   base64url от JSON `{id, clientDataJSON, authenticatorData, signature, userHandle}` (поля — base64url, не длиннее
   6144 символов). Поэтому неверные ответы считает штатный лимит ядра `FailedCodeAttemptsLimit`.
4. Сервер сначала **гасит вызов** (условный `UPDATE … WHERE isActive = 1`, выигрывает один запрос), потом проверяет
   ответ (§3). При успехе записывает счётчик под блокировкой строки `UserData` и повторно сверяет его с
   зафиксированным значением; ядро выдаёт токен. При отказе — 401, вызов уже израсходован.
5. После отказа или через 4 минуты шаг ключа сам повторяет первый запрос без кода и получает свежий вызов: пароль заново
   вводить не нужно. При 403 (лимит неудачных попыток) — сообщение. Если метод сменился или пароль больше не подходит,
   шаг возвращает на форму входа.
6. У пользователя с методом, но без читаемых ключей, второй шаг только объясняет, как восстановить вход
   (`itvolgaSecurityKeyNone`, `state: "noKeys"`, без вызова). Пропустить второй фактор нельзя.

### Настройка

1. «Безопасность» → включить 2FA, метод «Ключ безопасности (YubiKey)» → «Применить» → пароль (ядро проверяет его
   заново; администратор для другого пользователя вводит свой).
2. Окно модуля получает параметры регистрации (`getTwoFactorUserSetupData`): `rp`, `user` (id — внутренний id
   пользователя, без ПДн), вызов настройки (срок 15 минут), алгоритмы, `attestation: "none"`,
   `residentKey: "discouraged"`, `userVerification: "discouraged"`, `maxKeys: 5`.
3. «Добавить ключ» → `navigator.credentials.create`; уже добавленные в этом окне ключи передаются в
   `excludeCredentials` (повтор того же ключа — «Этот ключ уже добавлен»). Названия по умолчанию — «Основной»,
   «Запасной», «Ключ N».
4. «Применить» сохраняет модель `UserSecurity` одним `PUT` с атрибутом `itvolgaSecurityKeys`
   (`[{name, id, clientDataJSON, attestationObject, transports}]`). `verifyData` гасит вызов настройки, проверяет каждый
   ключ (§3), отклоняет повторы и заменяет весь набор. Затем ядро включает 2FA. Окно само вызывает `done`, поэтому
   закрывается и обязательное окно ядра.
5. Пока ключ регистрируется или набор сохраняется, в окне ничего нельзя изменить. Отказ — 403 ядра `Not verified.`:
   вызов израсходован, окно получает новый и начинает список заново. Перед этим окно сверяется с сервером
   (`GET UserSecurity/:id`): если метод уже включён, сохранение прошло и потерялся только ответ — окно завершается
   (окно открывается только когда метод ещё не включён, поэтому иначе быть не может).

### Сброс, отключение, смена метода

- Ключ добавляется позже штатным «Сбросить 2FA». Ядро сначала выдаёт параметры, потом сразу выключает 2FA; хук стирает
  прежние ключи. Пользователь регистрирует весь набор заново. Если закрыть окно, 2FA останется выключенной (так ядро
  ведёт себя и с TOTP).
- Потеряны все ключи — администратор снимает 2FA в карточке пользователя (`PUT UserSecurity/:id {auth2FA: false}`);
  хук стирает ключи; пользователь входит по паролю и настраивает заново. Кодов восстановления нет (D-130).
- Смена метода (например, на TOTP) — хук стирает ключи.
- Хук реагирует только на сохранение, которое **меняет** `auth2FA`/`auth2FAMethod`: `verifyData` записывает ключи своим
  сохранением, пока в БД ещё прежний метод, а ядро сохраняет новый метод следом (ORM пишет только изменённые поля).

## 3. Проверки (WebAuthn L2 §7.1, §7.2)

Общие: строгий base64url (алфавит, без `=`, каноническая форма, лимит до декодирования); clientDataJSON — JSON-объект
до 4 КБ, `type` (`webauthn.create`/`webauthn.get`), `challenge` (байты, `hash_equals`), `origin` — точное совпадение,
`crossOrigin` нет или `false`, `topOrigin` нет; authenticatorData — от 37 байт до 16 КБ, `rpIdHash` = SHA-256(RP ID),
флаг UP, BS без BE — отказ, после заявленных частей ничего нет; CBOR — только определённые длины, без тегов и float,
повтор ключа карты, глубина больше 8 и больше 64 элементов — отказ.

Регистрация: `attestationObject` — карта `fmt` (строка), `attStmt` (карта, пустая при `none`; у других форматов не
проверяется — политика «любой ключ»), `authData` (байты); флаг AT, id ключа 1–1023 байта и совпадает с присланным `id`;
COSE: ES256 — kty 2, crv P-256, x/y по 32 байта, точка на кривой (импорт OpenSSL); EdDSA — kty 1, crv Ed25519,
32 байта; RS256 — kty 3, модуль 2048–4096 бит, нечётный, показатель нечётный ≥ 3; другой alg — отказ.

Вход: id ключа есть среди ключей пользователя (поиск только у пользователя, прошедшего пароль); `userHandle`, если есть,
совпадает с id пользователя; AT нет; подпись над `authenticatorData || SHA-256(clientDataJSON)` (ES256 — DER ECDSA,
RS256 — PKCS#1 v1.5, Ed25519 — 64 байта); счётчик — если сохранённый или полученный не ноль, полученный должен быть
больше (иначе ключ мог быть клонирован; в журнал — warning). Ключи без счётчика (всегда 0) защищает только
одноразовый вызов.

Ошибки ядра проверки — `VerificationFailed` с кодом причины, без входных данных. В журнал — id пользователя и код
причины; браузеру — только 401.

## 4. Данные

- `UserData.cSecurityKeys` (jsonArray, только чтение): `[{id, algorithm, publicKey (SPKI DER), signCount, name,
  transports, createdAt, lastUsedAt}]`, двоичное — base64url. Не секрет (открытые ключи), но наружу не отдаётся: у
  `UserData` нет API, `GET UserSecurity/:id` отдаёт только флаг и метод.
- Вызовы — `TwoFactorCode`: `method` = `ItvolgaSecurityKey` (вход) или `ItvolgaSecurityKeySetup` (настройка), `code` —
  base64url вызова, `isActive`, `createdAt`. Старые записи удаляет штатная очистка ядра (5 дней).
- Уникальность id ключа между пользователями не проверяется: при входе ключ ищется только у пользователя, прошедшего
  пароль (D-129).

## 5. Конфигурация и окружение

- RP ID и origin — из `siteUrl`: origin = `scheme://host[:нестандартный порт]`, RP ID = host. Системный параметр
  `itvolgaSecurityKeyRpId` (не читается и не пишется через API; `task espo -- config:set itvolgaSecurityKeyRpId <домен>`)
  задаёт родительский домен; IP-адрес, схема не http(s) или чужой домен — «метод не настроен» (403
  `2faMethodNotConfigured` при настройке, ошибка входа и запись в журнал при входе).
- Ключ привязан к RP ID: смена домена или `siteUrl` делает все ключи недействительными. Ключи стенда на production не
  работают — после переключения пользователи регистрируют ключи заново.
- WebAuthn работает только в защищённом контексте. Production — только HTTPS (этап 09). Стенд — HTTP: в Chrome нужен флаг
  `chrome://flags/#unsafely-treat-insecure-origin-as-secure` = `http://crm.itvolga.test` (автопроверки — отдельный
  headless Chrome с `--unsafely-treat-insecure-origin-as-secure=http://crm.itvolga.test` и `--user-data-dir`). Без
  защищённого контекста шаг ключа сообщает, что нужен HTTPS, и предлагает только вернуться.
- Метод включает администратор («Доступные методы 2FA»); `task model:apply` его не включает. **Нельзя снимать метод из
  списка или выключать 2FA в настройках, пока им пользуются**: ядро тогда молча пропускает второй фактор
  (`Authentication::getUser2FAMethod`) — сначала перевести пользователей на другой метод.
- Нужны расширения PHP `openssl` и `sodium` (без sodium EdDSA не предлагается, сохранённые EdDSA-ключи не проходят) и
  64-битный PHP; проверить на production на этапе 09.

## 6. Найденная ошибка ядра 10.0.9

Вид входа ядра читает ответ первого шага как `xhr.responseJSON`, а объект запроса ядра (`util/ajax` `Xhr`, наследник
`XMLHttpRequest`) этого свойства не имеет. К тому же тело 401 отдаётся как `text/html`. Поэтому ядро теряет `message`,
`view` и `data` второго шага: у штатного шага TOTP нет подсказки, а метод не может назвать свой вид. Модуль добавляет
`Xhr.prototype` геттер `responseJSON`, который разбирает только ответ `401 second-step-required`
(`client/custom/modules/itvolga/src/login-response.js`, подключается видами входа модуля). При обновлении ядра проверить,
не исправлено ли это в ядре.

## 7. Проверки и тесты

- `task test:security-key` — чистое ядро, ключи генерирует сам прогон (OpenSSL, sodium).
- `task test:security-key-stand` — приёмка на стенде через API: программный «ключ» (`tests/security_key_stand/authenticator.php`
  на базе тестового `SoftAuthenticator`, ключи только в памяти процесса), синтетические пользователи. Негативные проверки
  разнесены по пользователям и ждут окна лимита ядра (больше 10 отказов с одного IP за 60 с блокируют вход с loopback).
- UI-фикстура: `tests/security_key_stand/ui_fixture.py create|delete` (пользователи `synth-sk-ui-key`,
  `synth-sk-ui-owner`, `synth-sk-ui-totp`; пароли и секрет TOTP — `/data/itvolga/espo-private/stand/evidence/security-key/ui-users.env`, 600).
- Итоги проверок и негативных контролей — `evidence.md`, раздел «Вне этапов — ключ безопасности».

## 8. Ограничения и не проверено

- Не проверено: Firefox и Safari, NFC и Bluetooth, YubiKey Bio, ключ с обязательным PIN, порталы (`auth2FAInPortal`
  выключен), production за обратным прокси.
- Шаг ключа и коды ядра переопределяют «приватные» методы вида входа ядра (`onSecondStepRequired`); при обновлении
  ядра проверить. Если ядро их переименует, коды TOTP/e-mail/SMS покажутся штатным видом (без фирменной рамки), а шаг
  ключа сервер всё равно назовёт сам.
- Сброс и отключение 2FA не отзывают уже выданные токены входа (поведение ядра).
- Счётчик повторно сверяется под блокировкой строки `UserData`, но подпись проверяется до блокировки: из двух
  одновременных ответов с одним и тем же счётчиком проходит один (ключи без счётчика защищает одноразовый вызов).
