# Импорт Vtiger (этапы 06.2–06.4)

Повторяемый импорт из проверенного защищённого снимка (`snapshot.md`) в EspoCRM: на этапе 06.2 — пользователи, контрагенты, контакты (и их доступы), обращения, сделки, календарь, заявки, комментарии и исторические проекты; на этапе 06.3 — финансы (предложения, заказы, акты, счета с позициями, платежи с распределением, юрлицо), товары и услуги, поставщики, документы, база знаний, письма, архивы и все файлы; на этапе 06.4 — дельта между пробным импортом и переключением (удаление исчезнувшего из источника, связи и смена типа активности по источнику, возврат финансов), полная сверка колонок всего снимка, налоги, прерывание и повтор. Решения — D-139…D-146 (06.2), D-147…D-153 (06.3), D-154…D-163 (06.4), сводка последнего прогона — `import-summary.md` (генерируется), проверки — `evidence.md`, «Этап 06.2», «Этап 06.3», «Этап 06.4».

```bash
task import:run -- --snapshot 20261006T201216            # backup стенда, импорт, проверочный проход, сверка
task import:run -- --snapshot <id> --check-only          # без записи: план и сверка с текущим состоянием
task import:run -- --snapshot <id> --only Users,Contacts # часть модулей (ссылки на остальные — «отложены»)
task import:run -- --snapshot <id> --allow-mass-removal  # пропустить предохранитель массового удаления (D-159)
task import:summary -- <прогон>                          # обезличенная сводка → docs/migration/import-summary.md
task import:drill -- --snapshot <id> [--restore <backup>] # учение: прерывание SIGTERM/SIGKILL, сходимость, повтор
task stand:fingerprint -- take <метка> | diff A B        # отпечаток стенда: CHECKSUM таблиц + sha256 хранилища
task snapshot:diff -- <A> <B> [--out …/snapshot-delta.md] # что изменилось в Vtiger между снимками (счётчики)
task test:stage06.2                                      # приёмочные тесты 06.2 на синтетике + чистые проверки
task test:stage06.3                                      # приёмочные тесты 06.3: финансы, файлы, паритет D-11
task test:stage06.4                                      # приёмочные тесты 06.4: дельта, прерывание, реестр, налоги
```

Коды выхода: `0` — всё сверено; `2` — находки (ожидание следующих этапов, конфликты источников, сохранённые в `vtigerData`, удержанные записи, расхождения итогов источника, принятые потери файлов, записи, удалённые или пересчитанные в EspoCRM, оставленные дельтой, пропущенный предохранитель); `1` — сбой (ошибка записи, расхождение при проверке, неучтённое значение, «шум» на стенде, проблема покрытия карт, неравные агрегаты, недоступный файл на стенде, живая запись вне источника после прогона, колонка снимка без судьбы, отказ предохранителя). Консоль показывает только шаги и счётчики.

| Часть | Файл | Что делает |
|---|---|---|
| Оркестратор | `scripts/import/importer.py` | покрытие карт → проверенный источник → план → запись → проверочный проход → «тишина» → сверка → приватный отчёт; `summary` |

| Запись | `task espo -- itvolga-import` (`Classes/ConsoleCommands/Import.php`, `Tools/Import/`) | поиск по `vtigerId` с удалёнными (или по естественному ключу — `KeyResolver::NATURAL_KEYS`), восстановление, принятие администратора, проверка значений по метаданным, запись только отличий, возврат того, что переписали хуки, удаление напоминаний, созданных ядром; финансовые правила (`FinanceRules`), файлы (`BlobReceiver`, `AttachmentWriter`), детали сверки документов (`FinanceCheck`); проверочный режим и перечень `vtigerId` цели |

| Агрегаты | `scripts/import/aggregates.py` | одни и те же меры финансов: SQL источника, план, SQL стенда — точные decimal |

**Передача значений.** Значения источника существуют только в памяти процесса разработчика и в анонимном канале stdin процесса PHP (`scripts/stand/espo.sh` → `sudo -u espocrm`): не в argv, не в окружении, не в файлах, доступных пользователю стенда (кроме самих файлов вложений в хранилище стенда — их место). Ответы PHP — строки `#itv#<случайная метка>#{json}` со статусом, id, именами атрибутов и закрытыми кодами ошибок; строки без метки (предупреждения PHP) только считаются. Тексты исключений не выводятся (SQL и PDO могут цитировать значения); журнал приложения на время команды заглушён (`NullHandler`): иначе упавший SQL записался бы в `data/logs` со значениями.

## Операция

Операция — желаемое состояние одной записи. Импорт **владеет** только тем, что в ней есть:

- `attributes` — все поля из правил, пустые — `null` (D-38: без умолчаний EspoCRM; у новых записей умолчания enum, не заданные правилами, обнуляются — например, направление звонка); `vtigerData` — объект целиком (кроме `ContactAccess`, у которого архива нет);
- `links` — ссылка `[тип, ключ источника]` или `null`; ссылка на модуль следующего этапа или не выбранный в `--only` — не передаётся (остаётся как есть);
- `linkMultiple` — элементы добавляются; `domain` — принадлежащее импорту множество: команды групп Vtiger и четыре роли Vtiger следуют источнику; `owned` (06.4, D-156) — элементы, указывающие на импортированные записи диапазона прогона, следуют источнику (снимаются, если источник их больше не связывает), элементы к записям, созданным в EspoCRM, остаются;
- `emails`, `phones` — набор целиком (источник побеждает); флаги общей записи адреса/номера сохраняются;
- `relate` — связи без поля «многие ко многим» (документ ↔ записи): список добавляет, `{"items": […], "owned": true}` (06.4) — источник владеет связями с импортированными записями, как у `owned`;
- `secret` — пароль доступа (сравнение расшифрованным), `preferences` — настройки пользователя, `user.adopt`, `keyAlsoIn` (другие типы активностей: живая запись другого типа с тем же ключом снимается в транзакции записи нового типа — D-157), `onlyIfExists` (доступ без значений: очищает существующий, пустой не создаёт);
- `remove` (протокол 3, 06.4) — запись, исчезнувшая из источника: тип и ключ, решение — у писателя (D-155).

## Повторный запуск

- Ключ — `vtigerId` (уникален вместе с удалёнными строками, D-41); у юрлица и категории базы знаний — естественный ключ (D-149): единственная живая запись, без живых — последняя удалённая (восстанавливается), несколько живых — ошибка `ambiguous_key`. Удалённая в EspoCRM запись восстанавливается (`restoreDeleted`, для пользователя — и `deleteId`), id сохраняется; финансовая — нет (D-148), кроме удалённой самой дельтой (`vtigerData.deletedInSource`, D-158).
- Источник побеждает: поля и одиночные ссылки приводятся к источнику. Неизменённая запись **не пишется** (ни `modifiedAt`, ни версия, ни шифротекст пароля); повторный запуск на стенде не изменил ни одной строки ни одной таблицы и ни одного файла хранилища (отпечатки до и после, `evidence.md`, «Этап 06.3»).
- Записи, исчезнувшие из источника, удаляются дельтой (06.4, D-155; раздел «Дельта»).
- Ключи `≥ 900 000 000` отведены тестам: реальный импорт отказывается от таких ключей источника, сверка показывает такие записи цели отдельно.

## Даты, авторы, тишина

- `createdAt`/`createdBy` записываются с `SaveOption::IMPORT`; `modifiedAt` новой записи ядро всегда ставит текущим — его, как и всё, что переписали хуки (`Opportunity.probability`, `Lead.convertedAt`, `Task.dateCompleted`, контакт задачи после `ParentLink`), возвращает один прямой `UPDATE` собственной строки после сохранения (`RecordWriter::force`, имена — в отчёте).
- Даты — D-30 (`transforms.to_utc`): Москва до 2022-11-01, Берлин до 2026-06-13, затем UTC; `TIMESTAMP` уже в UTC; поля «только дата» не сдвигаются. Срок задачи календаря — дата (`dateEndDate`); производный `dateEnd` (следующая полночь в поясе установки, как считает ядро) импорт задаёт сам. Несуществующее (перевод часов) или двойное местное время пересчитывается детерминированно и считается в отчёте (в снимке таких нет).
- Сохранение: `IMPORT` + `SILENT` + `NO_NOTIFICATIONS` + без хуков связей; комментарии — `SKIP_HOOKS` (их уведомления подписчикам, websocket и время потока родителя `SILENT` не учитывают). Напоминания, созданные ядром для импортированных событий по настройкам участников, удаляются. Проверка «тишины»: число строк уведомлений, напоминаний, подписок, записей ленты без `vtigerId`, писем без `vtigerId` (06.3: импортированные письма — ожидаемая запись), очереди вебхуков и журнала действий до и после прогона — равно.

## Преобразования (D-144)

- `vtigerData.<ключ>` — исходное значение, когда рабочее поле его не хранит дословно: колонки с судьбой «архив»; значение, заменённое словарём (ключ — имя поля Vtiger: `industry`, `accounttype`, `leadstatus`, `eventstatus`…); изменённый телефон или адрес (`phone`, `mobile`, `email1`…); нестандартное обращение (`salutationtype`); должность контакта без контрагента (`title`: в EspoCRM должность — роль связи с основным контрагентом); время без даты; длительность, не совпадающая с датами (`duration_hours`/`duration_minutes`); второй источник одиночной ссылки с другим значением (`<link>Alternatives`, никогда «последний победил»); лишние контакты «Письма» (`contactids`); другой автор комментария (`smcreatorid`).
- Телефоны (решение владельца 2026-10-11): 11 цифр с 7/8 и 10 цифр → `+7XXXXXXXXXX`, номер с `+` — без пробелов и скобок; местные, короткие, несколько номеров в одном значении — как в источнике. Тип номера хранится на общей записи номера: первый владелец по порядку импорта задаёт тип, у следующего с другим типом исходная колонка — в `vtigerData` (счётчик `type_conflict`); один номер дважды в записи — один номер + исходник.
- Текст — дословно, с пробелами по краям (полностью пустой — пусто); e-mail — в нижнем регистре, исходный вид — в `vtigerData`, если отличался.
- Настройки пользователя, которыми владеет импорт (язык, пояс, формат даты и времени, первый день недели, подпись), передаются всегда: пустое значение источника очищает настройку.
- Вид задачи («Письмо» или обычная) принадлежит импорту: «Письмо», ставшее задачей, теряет вид. Активность с пустым или неизвестным типом — ошибка записи.
- Дата и время активности (`date_start`+`time_start`, `due_date`+`time_end`) переносятся только парой; часть без пары остаётся в `vtigerData` под именем колонки; у звонка без полного окончания `dateEnd` = начало (D-43) и `vtigerData.dateEndMissing`.
- Тип общего номера определяется по всему источнику в порядке импорта (пользователи, контрагенты, контакты, обращения), а не только по модулям прогона.
- Ноль в числовых колонках с правилом «0 = пусто» (`employees`, `annualrevenue`, `noofemployees`, `hours`, `days`) и нулевые ссылки — пусто (исход `zero_empty`); вероятность сделки `0` — значение источника.

## Финансы (06.3, D-147, D-148)

- Запись — ORM с `IMPORT` + `SILENT` (иначе `FinanceSilentImport` отказывает): документ, затем каждая позиция отдельной операцией (позиции без документа писатель не создаёт: `unresolved_links`/`owner_missing`), платёж, затем его распределение. Хуки финансов не пересчитывают импортированное: номер, итоги и строки — как в источнике (D-05, D-17), юрлицо разрешается из `vtigerData.spcompany`, новое распределение проверяется (`AllocationWrites`: приход, одна цель, сумма ≤ платежа) и сразу пересчитывает оплату документа.
- После записи — только записи прогона (`--id` с id стенда; пустой выбор не передаётся — он означал бы все документы): `itvolga-finance-verify` по каждому типу документов (пометки «Пересчёт ядра»; сохраняет документ только при изменении пометок), `itvolga-finance-settle --silent` по счетам и заказам прогона и документам, на которые указывают его распределения до и после записи (пишет только изменения), затем `itvolga-finance-settle --dry-run` по тем же — изменений быть не должно; счётчики номеров — `itvolga-setup-finance --next=<cur_id снимка>` (только вверх; и в прогоне без документов, например `--only SPPayments`).
- Удалённое в EspoCRM не восстанавливается: запись, позиция или распределение удалённого документа/платежа — `deleted_in_target` (находка, проверочный проход отвечает так же). Ссылка на удалённую в EspoCRM запись не стирается и не ставится — `deletedTargets` (находка).
- Документ, пересчитанный в EspoCRM (`vtigerData.sourceTotals`): расчётные поля и позиции не пишутся и не сравниваются (`protected`), снимок `sourceTotals` сохраняется в `vtigerData`, остальное — источник побеждает. Запись документа или позиции первым делом блокирует строку документа (`FinanceRules::lock`, как `DocumentProcessor`): пересчёт, зафиксированный во время импорта, либо виден импорту, либо ждёт его — и не перезаписывается. Позиция, которую источник переносит в другой документ, из пересчитанного документа не уходит (`protected`). Документ с валютой, отличной от `currency_id = 1`, не пишется (ошибка записи `currency_unknown`). Платёж, чью сумму источник снижает ниже сохранённого распределения (хук платежа отказывает), пишется повторно после распределений того же прогона.
- После сохранения финансовой записи писатель возвращает только авторов и даты (`FinanceRules::FORCEABLE`): производные значения — хуков.

## Файлы (06.3, D-150, D-153)

- Источник — часть `vtiger` проверенного снимка: опись `inventory/vtiger.tsv` (запечатана, проверяется V1 при восстановлении), разрешение «вложение → файл» — правила проверки снимка (`verify.resolve_attachments`: варианты имени, затем единственный префикс `<id>_`; неоднозначное не принимается). Блокировка снимка держится весь прогон.
- Операция `Attachment` (ключ — `attachmentsid`; логотип — через `LegalEntity.logo`) несёт имя, тип, роль, описание (`vtigerData`), владельца и `file {size, sha256, chunks}`; за ней в stdin — `chunks` строк base64 по 3 МиБ. Строк всегда ровно `chunks`, что бы ни лежало в файле сейчас (короче описи — писатель отказывает по размеру, длиннее — прогон останавливается после кадров): следующая операция никогда не читается как кадр. Писатель пишет байты во временный файл рядом с хранилищем, сверяет размер и sha256 и только потом переименовывает файл в `data/upload/<id>`; совпадающий файл не переписывается; временный файл не переживает команду; файл нового вложения, чья транзакция не зафиксировалась (сохранение или сам `COMMIT`), удаляется, если записи вложения нет в базе. Ядро уменьшает счётчик транзакций до `PDO::commit()`: после сбоя `COMMIT` (любого сбоя после того, как запись вернулась) писатель сам завершает транзакцию и останавливается (`transaction_failed`) — прогон падает, а не пишет дальше в неопределённом состоянии.
- Владелец — явно: поле файла или изображения (`Document.file`, `Contact.cPhoto`, `User.avatar`, `LegalEntity.logo`) — `related` + `field` вложения и `<field>Id` владельца прямым `UPDATE` (сохранитель ядра удалил бы прежнее вложение); список вложений (`Note.attachments` — комментарии сохраняются без хуков, `Email.attachments`) — `parent`. Поля файлов импорт не очищает.
- Проверка каждого файла: проверочный проход (запись вложения, владелец, файл в хранилище с sha256 источника) и скачивание через стенд администратором (`?entryPoint=download`: 200 и sha256 источника, ответ владельца 2026-10-11). Приватный `files.jsonl` — по каждому файлу класс и причина; имя файла без файла в источнике — принятая потеря D-23 (`not_applicable:D-23`, имя в `vtigerData`); имя фото или аватара, отличное от имени его вложения, — в `vtigerData` и находка `file_name_differs`; в прогоне без `Attachments` имя ждёт (`deferred`): файл и указатель владельца проверяет операция вложения.
- Имя, размер и тип файла документа сверяются с вложением только в прогоне с `Attachments`; без него — ждут (`deferred`).
- Внешние документы — URL дословно в `cExternalUrl` (D-153), по сети не открываются; значение, не являющееся URL (схема http/https/ftp и хост, без пробелов, не длиннее 255), — в `vtigerData.filename` и находка `external_url_invalid`.

## Письма и база знаний (06.3, D-152)

- Письмо: `from`/`to`/`cc`/`bcc` — адреса в нижнем регистре через `;` (поля не хранимые: писатель загружает их из репозитория ядра и сравнивает множествами), `fromString` — дословно; JSON-список Vtiger без потерь — «нормализовано», иначе исходник в `vtigerData.<field>_email`. Родитель — `seactivityrel`, второй источник (`crmentityrel`) — дубликат или альтернатива (`parentAlternatives`); получатели `idlists` — дубликат родителя или `vtigerData.idlists`; трекинг (`vtiger_email_track`) — `vtigerData.track`. Связи писем с пользователями ядро ставит по адресам; импорт отмечает их прочитанными.
- Статья базы знаний: вопрос, ответ, номер, статус (словарь), категория «Общее» (`categories`, множество импорта — эта категория), теги — `cTags`, `type = Article`; комментарии к FAQ — `Note` с родителем-статьёй (лента статьи включена).

## Сверка

Приватный каталог прогона `/data/itvolga/espo-private/import/<прогон>/` (700/600): `report.json` (итоги и счётчики), `records.jsonl` (по каждой записи: ключ, id, статусы записи и проверки, имена изменённых/возвращённых/расходящихся атрибутов, исходы колонок — без значений), `logs/`.

- **Колонки.** Все колонки всех прочитанных таблиц по живым записям модуля (не только строки карты). Перепись SQL и подсчёт прочитанного Python обязаны совпасть (иначе запись не начинается). Для колонок с правилом каждое непустое значение получает один исход (`carried`, `normalized`, `mapped`, `archived`, `linked`, `protected`, `derived_equal`, `duplicate`, `type_conflict`, `no_target`, `zero_empty`, `pending:<этап>`, `deferred`, `dangling:<причина>`, `not_applicable:<причина>`); неучтённое значение — сбой. Перенесённые значения сверены **проверочным проходом** (отдельный процесс, без записи: желаемое состояние сравнивается с сохранённым). Колонки без правила: ключи, «исключено» (судьба из карты), «пусто по карте» (значимое значение в такой колонке — находка «карта устарела»), «без строки карты» (непустое — сбой).
- **Связи.** Каждая строка таблиц связей источника в границах этапа (SQL-перепись по тем же условиям, что и чтение) получает один исход (`linked`, `duplicate`, `conflict`, `pending:<этап>`, `dangling`, `no_target`); перенесённые сверены проверочным проходом; пара модулей, неизвестная спецификации, — сбой (`unhandled_relations`). Колонки таблиц связей имеют явную судьбу (`spec.LINK_COLUMNS`): «пара» — из них строится связь; «ждёт этапа»; «не переносится» с причиной — автор и время постановки тега, видимость и автор тега Vtiger, нормализованная форма тега (значение тега — `raw_tag`), описание группы; непустая колонка без судьбы — сбой.
- **Записи без основной строки.** Живая запись `vtiger_crmentity` без строки основной таблицы модуля (её не прочитал бы `JOIN`) считается отдельно — сбой `live_without_base_row`.
- **Второй источник одиночной ссылки** (`crmentityrel` после поля или `seactivityrel`): та же цель — дубликат, другая — альтернатива в `vtigerData.<link>Alternatives`; отложенная первая ссылка (цель следующего этапа) не перебивается. Строка `crmentityrel`, модули которой не совпадают с фактическими модулями записей, не связывается (находка); писатель отклоняет ссылку на запись другого типа.
- **Ручные связи под хуками ядра**: очистка основного контрагента контакта или основного контакта сделки/заявки по источнику снимает в ядре и элемент связи «многие ко многим» — писатель возвращает его вместе с колонками (роль), если элемент остаётся в итоговом множестве (06.4: элемент, снятый по источнику, не возвращается) и связь не стала основной по источнику.
- **Проверочный режим** (`--check-only`): отсутствующая запись — ожидаемо (её колонки и связи не сравниваются), расхождение существующей — сбой.
- **Частичный прогон** (`--only`): ссылки на пользователей без `Users` откладываются, как и на другие невыбранные модули; колонки невыбранных модулей помечаются «не выбрано», перепись строк связей сравнивается только в полном прогоне; одиночные ссылки на невыбранные модули (и должность контакта при невыбранном контрагенте, и выведенный контакт задачи) не трогаются, а писатель возвращает их значения, если их изменил хук сохранения (`keep`).
- **Записи.** По каждой сущности: источник, итог записи (`created`, `updated`, `restored`, `adopted`, `unchanged`, `skipped`, `error`), итог проверки (`equal`, `differs`, `missing`, `absent`), удержанные (ожидают этапа или пропущены с причиной); цель: живые записи с `vtigerId`, которых нет в источнике.

Ограничения:
- запись — по одной транзакции на запись: прерванный прогон может оставить документ без части позиций; проверочный проход это покажет (`missing`), повторный запуск достроит;
- файл в хранилище не откатывается вместе с транзакцией: новый файл удаляется при ошибке сохранения его вложения, а при падении процесса может остаться файл без записи (временные файлы `.itvolga-import-*` удаляются в конце команды);
- проверка «тишины» считает строки всей базы стенда — параллельная работа на стенде во время импорта даст ложное расхождение, а замена одной строки другой (например, подписки) счётчиком не видна;
- хук ядра `CaseObj/Contacts` при смене контакта заявки подписывает и отписывает портальных пользователей контакта и при `SILENT`; портал не используется (портальных пользователей нет, D-15);
- журнал MySQL `binlog` стенда и его backup содержат импортированные данные (решение владельца 2026-10-11), хранилище `data/upload` стенда — файлы вложений;
- записи цели, исчезнувшие из источника, удаляются (D-155); оставленные политикой (пересчитанный документ и его позиции, администратор) перечисляются в приватном `report.json` (тип и `vtigerId`);
- ядро EspoCRM физически вычищает мягко удалённые записи через `cleanupDeletedRecordsPeriod` (по умолчанию 2 месяца; на стенде `cleanupDeletedRecords = true`, проверено 2026-10-12): после этого «надгробия» D-148 (удалено в EspoCRM — не восстанавливать) и отметки дельты `deletedInSource` исчезают — финансовую запись, удалённую вручную больше двух месяцев назад, импорт создаст заново. Для production — решение этапа 09 (не чистить до последней дельты);
- хуки календаря ядра отправляют websocket и при `SILENT`; на стенде websocket выключен (`useWebSocket = false`), на production — проверить на этапе 09.

## Сверка финансов (06.3, D-151)

- Каждый документ: проверочный проход отдаёт результат `SourceVerifier` — класс формулы, каждый итог `exact`/`rounded`/`mismatch`, маржи строк, причины (закрытые коды), пересчитанные итоги, если итог не точен, и совпадение хранимых пометок с вычисленными. Каждое расхождение — строка приватного `discrepancies.jsonl` с причиной: `rounded_to_kopecks`, `stored_total_differs_from_source_formula`, `unsupported_source_formula`, `margin_differs_from_net_less_purchase_cost`, `linked_invoice_act_totals_differ`; в сводке — только счётчики.
- Каждое значение: номера, даты, статусы, валюта (`currency_id` = 1 → RUB у каждого денежного поля), суммы и ставки налога — колонки с правилом, сверенные проверочным проходом по каждой записи.
- Агрегаты (`aggregates.py`, приватный `aggregates.json`): количество и суммы итогов, скидок, доставки, корректировки, баланса; позиций — количества, цены, скидки, ставки, маржи, суммы; платежей по направлениям и распределений по целям; налоги (06.4, D-161): число документов по режиму налога, ставка налога доставки, налог по итогам (`итог − до налога − корректировка`) и число документов с ним, ставки 2 и 3 строк, налог заголовка (`cf.tax`), число строк с налогом — всего 112 мер; SQL источника = план (все записи; проверка чтения), план = SQL стенда (импортированные записи без D-148; проверка записи). Любое неравенство — сбой. Распределения в SQL источника — правило D-11, записанное второй раз независимо от порта планировщика (`aggregates.ALLOCATED`). Суммы — в точном контексте `Decimal` (200 знаков, неточность — исключение); сумма строки позиции (`exact_net`) так же: больше 8 знаков после запятой — ошибка `amount_scale`, не округление.
- Распределения: категории D-11 считаются в плане (`allocation:<категория>:<решение>`), конфликты и связи расходов — находки с исходником в `vtigerData`; после пересчёта оплаты пробный пересчёт не должен ничего менять.

## Карта и пробелы карты

Покрытие проверяется до чтения источника (`spec.check_coverage`): каждая колонка модулей этапа с судьбой переноса должна иметь правило, правило — строку карты; строки ключей (`(ключ записи)`, `vtigerId`, `<Сущность>.vtigerId`) правила не требуют. Исключения (`spec.MAP_GAPS`, D-146, D-149): `vtiger_crmentity.modifiedby` комментариев (ModComments не объявляет поле в `vtiger_field`, и аудит его не видит) → `Note.modifiedBy`; имя вложения (строка карты есть только у писем) → `Attachment.name`; автор писем → `Email.createdBy`; ответственный статей FAQ → `KnowledgeBaseArticle.assignedUser`; автор и изменивший чатов Jivosite/JVmes → `VtigerArchive.data`. Явные судьбы без строки карты (`spec.EXTRA_FATES`): служебные колонки события у писем (`notime`, `sendnotification`, `visibility`) — «исключено». Общая таблица строк документов (`vtiger_inventoryproductrel`) переписывается в каждом модуле документа по его живым документам.

## Дельта (06.4, D-154…D-159)

Между пробным импортом и переключением Vtiger продолжает работать. Повторное снятие — новый защищённый снимок (`task snapshot:create`, только чтение production), применение — тот же импорт по нему: `task import:run -- --snapshot <новый>`. План прогона — полное желаемое состояние нового снимка; разница снимков (`task snapshot:diff`, `snapshot.md`) — сводка «что изменилось в Vtiger», план она не задаёт: прогон сходится к источнику, с какого бы состояния стенда он ни начинал (прерванный прогон, прогон по старому снимку, частичный прогон).

Порядок прогона: чтение снимка → план → **инвентаризация цели** (ключи `vtigerId` живых, удалённых и неактивных записей каждого типа прогона; без значений) → план удалений (`removals.py`) и предохранитель → «тишина» до → запись: upsert в `spec.ORDER`, затем удаления в обратном порядке (дети раньше владельцев; финансовый документ — раньше своих позиций), затем повтор упавших платежей → постобработка финансов → проверочный проход (upsert, удаления, повторная инвентаризация) → «тишина» после (за вычетом ожидаемых эффектов удалений) → сверка.

- **Типы прогона** — те, все модули которых выбраны (`spec.owned_types`): только они удаляются и только на них распространяется владение связями (`Product` — при Products и Services, `VtigerArchive` — при всех архивах). Протокол писателя 3: заголовок несёт `keyRange` (реальные ключи или блок теста) и `ownedTypes` — писатель отказывает в удалении другого типа или ключа (`bad_operation`); сессии записи и проверки — ещё `removing` (ключи финансовых документов и позиций, которые прогон удаляет, см. «Удаления»).
- **Удаления** (D-155): запись цели удаляется, если она жива, её ключ в диапазоне прогона и её нет ни среди операций плана, ни среди удержанных (ошибка, ожидание этапа; распределение удержанного платежа и распределение, неразрешённое по D-11, — тоже удержаны, `Plan.held_keys`). Типы модуля, у которого в источнике есть живые записи без основной строки (`live_without_base_row`), не удаляются в этом прогоне (`removals.blocked`): их отсутствие в плане ничего не доказывает. Тихое мягкое удаление ядра (`IMPORT` + `SILENT` + `NO_NOTIFICATIONS`; комментарии — без хуков). Пользователь — деактивируется (администратор — `kept: administrator`); юрлицо и категория БЗ не удаляются никогда. Финансы — через свои хуки под блокировками в порядке стороны платежей (журнал платежей → строка платежа или документа; позиция — строка её документа); **все блокировки удаления берутся до первого обычного чтения** его транзакции — журнал платежей (у платежа, распределения, счёта, заказа и их позиций), строка документа позиции (её id читается до транзакции отдельным запросом), затем собственная строка записи вместе с «надгробием» (`RowLock::lockWithDeleted`): каскад ядра (`cascadeRemoval`) читает связанные записи обычным согласованным чтением, и снимок, открытый до ожидания, показал бы распределение там, откуда его уже перенесли (каскад удалил бы чужое распределение), а запись, удалённую пользователем во время ожидания, — живой (удаление дельты пометило бы ручное удаление `deletedInSource`, D-148). Распределения снимаются, оплата пересчитывается хуками и затем `itvolga-finance-settle` по документам прогона и целям снятых распределений. Документ остаётся (находка `kept_in_target:<причина>`): пересчитанный в EspoCRM — `recalculated_in_target`; документ, на который ещё указывает импортированное распределение (не входит в прогон или удержано), — `allocated_in_target` (хук документа снял бы распределение без отметки, и вернуть его было бы нельзя; в полном прогоне распределение снимается раньше своей операцией); документ с живой импортированной позицией, которую прогон не удаляет (другой диапазон ключей, удержана ошибкой, …), — `items_outside_run` (каскад ядра удалил бы её). Документ идёт **раньше своих позиций**: его удаление забирает позиции в той же транзакции (каскад ядра, та же отметка `deletedInSource`; операция позиции отвечает `removed`, `by: document`), оставленный документ сохраняет итоги, распределения и позиции — позиция живого документа, который прогон удаляет, остаётся с его причиной (`document_not_removed`, если операция документа упала); позиция документа, который в источнике есть, удаляется своей операцией (кроме пересчитанного документа). Устаревшие позиции изменённого документа (Vtiger при каждой правке пересоздаёт все строки с новыми `lineitem_id`, `include/utils/InventoryUtils.php`) удаляются так же (`removedByEdit`). Удалённое вложение: указатель поля владельца очищается, если всё ещё указывает на него; байты удаляет хук ядра `Attachment/RemoveFile`. Доступ контакта — отдельной операцией перед контактом. Платёж, чей `related_to` указывает на документ, удалённый в Vtiger, — исход `dangling:deleted` (распределения нет, прежнее удаляется).
- **Предохранитель** (D-159): до любой записи — отказ, если по типу к удалению больше `max(25, 5 %)` его живых записей диапазона или источник не содержит ни одной записи типа, а цель содержит; `--allow-mass-removal` пропускает (находка `mass_removal_allowed`). План удалений — приватный `removal-plan.json` (ключи по типам).
- **Связи** (D-156): `owned`-ссылки и связи документа следуют источнику между импортированными записями (раздел «Операция»); элемент, который ставит само ядро (ответственный — участник звонка/встречи, соисполнитель задачи), не снимается — иначе каждый прогон спорил бы с хуком. Снятые элементы — счётчики `removed_links` отчёта.
- **Смена типа активности** (D-157): операция нового типа находит живую запись того же ключа в другом типе (`keyAlsoIn`), создаёт или восстанавливает свою и в той же транзакции переносит напоминания и мягко удаляет прежнюю; заметки EspoCRM у прежней — находка `retyped_notes_left`. Проверочный проход видит оставшуюся живой прежнюю запись (`retype.<Тип>`).
- **Возврат** (D-158): финансовая запись, удалённая дельтой, несёт `vtigerData.deletedInSource` (ставит хук `Hooks/Common/FinanceDeltaMark` по опции удаления дельты; любое другое удаление отметку стирает); вернувшаяся в источник — восстанавливается (те же id), с позициями и распределением, `removedByEdit`/`removedWith` сбрасываются; решение принимается под блокировкой самого «надгробия» (`RowLock::lockWithDeleted`: документ — его строка; платёж и распределение — сначала журнал платежей, затем своя строка), так что ручное восстановление и повторное удаление, зафиксированные во время прогона, видны импорту; удалённая вручную — по-прежнему `deleted_in_target`, в том числе восстановленная и снова удалённая пользователем запись дельты.
- **Проверка**: удаление — проверочным проходом (`removed`, `kept` или `live` — проблема `removal_not_applied`); затем по новой инвентаризации — ни одной живой записи вне источника, кроме оставленных (проблема `live_outside_source`), и ни одной прежней записи сменившей тип (`retype_incomplete`). `--check-only` показывает удаления как находки `would_remove`, предохранитель — `mass_removal_refused`.
- **Тишина**: удаление события физически удаляет его напоминания (репозиторий ядра) — писатель считает их до удаления (`effects.reminder`), и «тишина» сравнивается за вычетом этого ожидаемого эффекта (`silence_expected`).

## Полная сверка колонок (06.4, D-160)

`ledger.py` после сверки прогона: каждая непустая колонка каждой таблицы обеих схем снимка — по счётчикам `tables.json`, которые сервер production посчитал в транзакции снимка, — получает класс:

| Класс | Что значит |
|---|---|
| `import` | таблица, которую читает импорт: значения живых записей в границах импорта сверены по одному (исходы и проверочный проход, раздел «Сверка»), значения удалённых в Vtiger записей — отдельный счётчик (`deleted`, перепись `source.deleted_census`), остальное (`outside_scope`: строки модулей, которые не переносятся, записи вложений, строки без записи) — с судьбами карты этих модулей |
| `configuration`, `module_code`, `excluded`, `key`, `empty` | таблица, которую импорт не читает, — по судьбе её строк карты (опции и настройки проверяет `task model:check`, печатные формы и отчёты — код модуля, исключённое — с причиной карты) |
| `pending:07.2` | телефония: таблицы PBXManager/SPCallPopup и вся схема `asteriskcdrdb` |

Сбой (проблемы `ledger_*`): `no_fate` — непустая колонка без строки карты и без судьбы спецификации (`LINK_COLUMNS`, `MAP_GAPS`, `EXTRA_FATES`) — в любой таблице, и в той, что читает импорт (значения могут лежать только в удалённых записях; новое поле или таблица Vtiger), `transfer_unread` — судьба «перенос»/«архив» у таблицы, которую импорт не читает, `unknown_fate`, `counts_disagree` — перепись импорта больше счётчика сервера, `maps_outdated` — карты, пересобранные по снимку его последней проверкой (`reports/verify-*/audit/maps/`, отчёт привязан к печати снимка), расходятся с картами Git **сейчас** (решения и судьбы, правило C4/C5) или проверки нет. Приватно — `ledger.jsonl` (имена и счётчики), в сводке — классы.

## Прерывание и повтор (06.4, D-162)

- Прогон — последовательность транзакций по одной записи: прерванный прогон оставляет завершённые записи, следующий прогон сходится (неизменённое не пишется). Журнал `applied.jsonl` — для уборки тестов и доказательств, не точка возобновления.
- Клиенты писателя и MySQL запускаются в своей группе процессов (`common.Mysql.session`): SIGTERM/Ctrl+C импортёра останавливает всю группу (bash → sudo → php: SIGTERM, через 15 с SIGKILL всему, что осталось в группе, — не только её лидеру; участник другого пользователя — через `sudo kill`), затем закрывает поток операций (не раньше: поток, заблокированный на полном канале, держит блокировку буфера); незавершённая транзакция откатывается MySQL.
- Байты файла переносятся в хранилище только после `COMMIT` записи вложения: убитый писатель не оставляет файла без записи (в худшем случае — запись без файла, её видит проверочный проход и дописывает следующий прогон). Сеанс записи держит исключительную блокировку (`data/.itvolga-import.lock`, второй писатель — `busy`) и сначала удаляет `.part`-файлы убитого писателя (`swept` в отчёте).
- Учение `task import:drill -- --snapshot <id> [--restore <backup>]` (protocol — `IMPORT_ROOT/drills/<время>/protocol.json`): backup стенда (защищённая копия), при `--restore` — восстановление прежнего backup (код не трогается), прогон A — SIGTERM после N записей (код 130, писателей не осталось), прогон B — SIGKILL импортёра и писателя во время передачи файлов, прогон C — сходится без проблем, прогон D — ничего не пишет (итог `pass` — только если каждый шаг дал ожидаемый код выхода и отчёт без проблем; любой выход учения — сбой шага, ошибка, SIGTERM, Ctrl+C — сначала останавливает всю группу процессов каждого ещё живого прогона): отпечатки `task stand:fingerprint` до и после него равны (CHECKSUM всех таблиц стенда, кроме журналов `job`, `scheduled_job`, `scheduled_job_log_record`, `auth_token`, `auth_log_record`, и sha256 каждого файла хранилища).
