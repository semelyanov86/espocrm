# Импорт базовых сущностей (этап 06.2)

Повторяемый импорт пользователей, контрагентов, контактов (и их доступов), обращений, сделок, календаря, заявок, комментариев и исторических проектов из проверенного защищённого снимка (`snapshot.md`) в EspoCRM. Решения — D-139…D-146, сводка последнего прогона — `import-summary.md` (генерируется), проверки этапа — `evidence.md`, «Этап 06.2».

```bash
task import:run -- --snapshot 20261006T201216            # backup стенда, импорт, проверочный проход, сверка
task import:run -- --snapshot <id> --check-only          # без записи: план и сверка с текущим состоянием
task import:run -- --snapshot <id> --only Users,Contacts # часть модулей (ссылки на остальные — «отложены»)
task import:summary -- <прогон>                          # обезличенная сводка → docs/migration/import-summary.md
task test:stage06.2                                      # приёмочные тесты на синтетике + чистые проверки
```

Коды выхода: `0` — всё сверено; `2` — находки (ожидание следующих этапов, конфликты источников, сохранённые в `vtigerData`, удержанные записи); `1` — сбой (ошибка записи, расхождение при проверке, неучтённое значение, «шум» на стенде, проблема покрытия карт). Консоль показывает только шаги и счётчики.

## Устройство

| Часть | Файл | Что делает |
|---|---|---|
| Оркестратор | `scripts/import/importer.py` | покрытие карт → проверенный источник → план → запись → проверочный проход → «тишина» → сверка → приватный отчёт; `summary` |
| Чтение | `scripts/import/source.py` | сессии `READ ONLY`, `sql_log_bin=0`, UTC; значения — `HEX(CONVERT(… USING utf8mb4))`; запрещённые колонки (пароли и хеши пользователей, адреса и домашние телефоны сотрудников) не читаются; перепись непустых значений каждой колонки SQL-выражением аудита (`gen_sql.nonempty_expr`) |
| Спецификация | `scripts/import/spec.py` | правила по модулям (колонка → поле, словарь, архив, телефон, ссылка…), операции (желаемое состояние записи), исходы каждого непустого значения, связи, проверка покрытия `field-map.csv`/`relations.csv` |
| Преобразования | `scripts/import/transforms.py` | D-30, телефоны, даты, десятичные, словари `vtigerValueMap` |
| Источник | `scripts/snapshot/verify.py` `restored_databases()` | V1, V0, V3 снимка, восстановление во временную базу стенда, V4; база живёт только на время чтения и удаляется по точному имени |
| Запись | `task espo -- itvolga-import` (`Classes/ConsoleCommands/Import.php`, `Tools/Import/`) | поиск по `vtigerId` с удалёнными, восстановление, принятие администратора, проверка значений по метаданным, запись только отличий, возврат того, что переписали хуки, удаление напоминаний, созданных ядром; проверочный режим и перечень `vtigerId` цели |

**Передача значений.** Значения источника существуют только в памяти процесса разработчика и в анонимном канале stdin процесса PHP (`scripts/stand/espo.sh` → `sudo -u espocrm`): не в argv, не в окружении, не в файлах, доступных пользователю стенда. Ответы PHP — строки `#itv#<случайная метка>#{json}` со статусом, id, именами атрибутов и закрытыми кодами ошибок; строки без метки (предупреждения PHP) только считаются. Тексты исключений не выводятся (SQL и PDO могут цитировать значения); журнал приложения на время команды заглушён (`NullHandler`): иначе упавший SQL записался бы в `data/logs` со значениями.

## Операция

Операция — желаемое состояние одной записи. Импорт **владеет** только тем, что в ней есть:

- `attributes` — все поля из правил, пустые — `null` (D-38: без умолчаний EspoCRM; у новых записей умолчания enum, не заданные правилами, обнуляются — например, направление звонка); `vtigerData` — объект целиком (кроме `ContactAccess`, у которого архива нет);
- `links` — ссылка `[тип, ключ источника]` или `null`; ссылка на модуль следующего этапа или не выбранный в `--only` — не передаётся (остаётся как есть);
- `linkMultiple` — элементы добавляются (связи, сделанные в EspoCRM вручную, остаются); `domain` — принадлежащее импорту множество: команды групп Vtiger и четыре роли Vtiger следуют источнику;
- `emails`, `phones` — набор целиком (источник побеждает); флаги общей записи адреса/номера сохраняются;
- `secret` — пароль доступа (сравнение расшифрованным), `preferences` — настройки пользователя, `user.adopt`, `keyAlsoIn` (другие типы активностей: смена типа источника — ошибка `type_changed`, политика — дельта 06.4), `onlyIfExists` (доступ без значений: очищает существующий, пустой не создаёт).

## Повторный запуск

- Ключ — `vtigerId` (уникален вместе с удалёнными строками, D-41). Удалённая в EspoCRM запись восстанавливается (`restoreDeleted`, для пользователя — и `deleteId`), id сохраняется.
- Источник побеждает: поля и одиночные ссылки приводятся к источнику. Неизменённая запись **не пишется** (ни `modifiedAt`, ни версия, ни шифротекст пароля); третий подряд запуск на стенде не изменил ни одной строки (отпечатки до и после, `evidence.md`).
- Записи, исчезнувшие из источника, не удаляются — только перечисляются (политика удаления — дельта 06.4).
- Ключи `≥ 900 000 000` отведены тестам: реальный импорт отказывается от таких ключей источника, сверка показывает такие записи цели отдельно.

## Даты, авторы, тишина

- `createdAt`/`createdBy` записываются с `SaveOption::IMPORT`; `modifiedAt` новой записи ядро всегда ставит текущим — его, как и всё, что переписали хуки (`Opportunity.probability`, `Lead.convertedAt`, `Task.dateCompleted`, контакт задачи после `ParentLink`), возвращает один прямой `UPDATE` собственной строки после сохранения (`RecordWriter::force`, имена — в отчёте).
- Даты — D-30 (`transforms.to_utc`): Москва до 2022-11-01, Берлин до 2026-06-13, затем UTC; `TIMESTAMP` уже в UTC; поля «только дата» не сдвигаются. Срок задачи календаря — дата (`dateEndDate`); производный `dateEnd` (следующая полночь в поясе установки, как считает ядро) импорт задаёт сам. Несуществующее (перевод часов) или двойное местное время пересчитывается детерминированно и считается в отчёте (в снимке таких нет).
- Сохранение: `IMPORT` + `SILENT` + `NO_NOTIFICATIONS` + без хуков связей; комментарии — `SKIP_HOOKS` (их уведомления подписчикам, websocket и время потока родителя `SILENT` не учитывают). Напоминания, созданные ядром для импортированных событий по настройкам участников, удаляются. Проверка «тишины»: число строк уведомлений, напоминаний, подписок, записей ленты без `vtigerId`, писем, очереди вебхуков и журнала действий до и после прогона — равно.

## Преобразования (D-144)

- `vtigerData.<ключ>` — исходное значение, когда рабочее поле его не хранит дословно: колонки с судьбой «архив»; значение, заменённое словарём (ключ — имя поля Vtiger: `industry`, `accounttype`, `leadstatus`, `eventstatus`…); изменённый телефон или адрес (`phone`, `mobile`, `email1`…); нестандартное обращение (`salutationtype`); должность контакта без контрагента (`title`: в EspoCRM должность — роль связи с основным контрагентом); время без даты; длительность, не совпадающая с датами (`duration_hours`/`duration_minutes`); второй источник одиночной ссылки с другим значением (`<link>Alternatives`, никогда «последний победил»); лишние контакты «Письма» (`contactids`); другой автор комментария (`smcreatorid`).
- Телефоны (решение владельца 2026-10-11): 11 цифр с 7/8 и 10 цифр → `+7XXXXXXXXXX`, номер с `+` — без пробелов и скобок; местные, короткие, несколько номеров в одном значении — как в источнике. Тип номера хранится на общей записи номера: первый владелец по порядку импорта задаёт тип, у следующего с другим типом исходная колонка — в `vtigerData` (счётчик `type_conflict`); один номер дважды в записи — один номер + исходник.
- Текст — дословно, с пробелами по краям (полностью пустой — пусто); e-mail — в нижнем регистре, исходный вид — в `vtigerData`, если отличался.
- Настройки пользователя, которыми владеет импорт (язык, пояс, формат даты и времени, первый день недели, подпись), передаются всегда: пустое значение источника очищает настройку.
- Вид задачи («Письмо» или обычная) принадлежит импорту: «Письмо», ставшее задачей, теряет вид. Активность с пустым или неизвестным типом — ошибка записи.
- Дата и время активности (`date_start`+`time_start`, `due_date`+`time_end`) переносятся только парой; часть без пары остаётся в `vtigerData` под именем колонки; у звонка без полного окончания `dateEnd` = начало (D-43) и `vtigerData.dateEndMissing`.
- Тип общего номера определяется по всему источнику в порядке импорта (пользователи, контрагенты, контакты, обращения), а не только по модулям прогона.
- Ноль в числовых колонках с правилом «0 = пусто» (`employees`, `annualrevenue`, `noofemployees`, `hours`, `days`) и нулевые ссылки — пусто (исход `zero_empty`); вероятность сделки `0` — значение источника.

## Сверка

Приватный каталог прогона `/data/itvolga/espo-private/import/<прогон>/` (700/600): `report.json` (итоги и счётчики), `records.jsonl` (по каждой записи: ключ, id, статусы записи и проверки, имена изменённых/возвращённых/расходящихся атрибутов, исходы колонок — без значений), `logs/`.

- **Колонки.** Все колонки всех прочитанных таблиц по живым записям модуля (не только строки карты). Перепись SQL и подсчёт прочитанного Python обязаны совпасть (иначе запись не начинается). Для колонок с правилом каждое непустое значение получает один исход (`carried`, `normalized`, `mapped`, `archived`, `linked`, `protected`, `derived_equal`, `duplicate`, `type_conflict`, `no_target`, `zero_empty`, `pending:<этап>`, `deferred`, `dangling:<причина>`, `not_applicable:<причина>`); неучтённое значение — сбой. Перенесённые значения сверены **проверочным проходом** (отдельный процесс, без записи: желаемое состояние сравнивается с сохранённым). Колонки без правила: ключи, «исключено» (судьба из карты), «пусто по карте» (значимое значение в такой колонке — находка «карта устарела»), «без строки карты» (непустое — сбой).
- **Связи.** Каждая строка таблиц связей источника в границах этапа (SQL-перепись по тем же условиям, что и чтение) получает один исход (`linked`, `duplicate`, `conflict`, `pending:<этап>`, `dangling`, `no_target`); перенесённые сверены проверочным проходом; пара модулей, неизвестная спецификации, — сбой (`unhandled_relations`). Колонки таблиц связей имеют явную судьбу (`spec.LINK_COLUMNS`): «пара» — из них строится связь; «ждёт этапа»; «не переносится» с причиной — автор и время постановки тега, видимость и автор тега Vtiger, нормализованная форма тега (значение тега — `raw_tag`), описание группы; непустая колонка без судьбы — сбой.
- **Записи без основной строки.** Живая запись `vtiger_crmentity` без строки основной таблицы модуля (её не прочитал бы `JOIN`) считается отдельно — сбой `live_without_base_row`.
- **Второй источник одиночной ссылки** (`crmentityrel` после поля или `seactivityrel`): та же цель — дубликат, другая — альтернатива в `vtigerData.<link>Alternatives`; отложенная первая ссылка (цель следующего этапа) не перебивается. Строка `crmentityrel`, модули которой не совпадают с фактическими модулями записей, не связывается (находка); писатель отклоняет ссылку на запись другого типа.
- **Ручные связи под хуками ядра**: очистка основного контрагента контакта или основного контакта сделки/заявки по источнику снимает в ядре и элемент связи «многие ко многим» — писатель возвращает его вместе с колонками (роль), если связь не стала основной по источнику.
- **Проверочный режим** (`--check-only`): отсутствующая запись — ожидаемо, расхождение существующей — сбой.
- **Частичный прогон** (`--only`): колонки невыбранных модулей помечаются «не выбрано», перепись строк связей сравнивается только в полном прогоне; одиночные ссылки на невыбранные модули (и должность контакта при невыбранном контрагенте, и выведенный контакт задачи) не трогаются, а писатель возвращает их значения, если их изменил хук сохранения (`keep`).
- **Записи.** По каждой сущности: источник, итог записи (`created`, `updated`, `restored`, `adopted`, `unchanged`, `skipped`, `error`), итог проверки (`equal`, `differs`, `missing`, `absent`), удержанные (ожидают этапа или пропущены с причиной); цель: живые записи с `vtigerId`, которых нет в источнике.

Ограничения: проверка «тишины» считает строки всей базы стенда — параллельная работа на стенде во время импорта даст ложное расхождение; журнал MySQL `binlog` стенда и его backup содержат импортированные данные (решение владельца 2026-10-11).

## Карта и пробелы карты

Покрытие проверяется до чтения источника (`spec.check_coverage`): каждая колонка модулей этапа с судьбой переноса должна иметь правило, правило — строку карты. Единственное задокументированное исключение (`spec.MAP_GAPS`): `vtiger_crmentity.modifiedby` комментариев (78 значений) переносится в `Note.modifiedBy`, хотя строки карты нет — ModComments не объявляет это поле в `vtiger_field`, и аудит его не видит.
