# Защищённый снимок источника (этап 06.1)

Снимок — полная read-only копия источника на один момент: базы `vtiger7` и `asteriskcdrdb`, файлы Vtiger (вложения, логотипы, `test/upload`), CDR CSV и записи разговоров. Из снимка читают импорт (06.2–06.4), история звонков (07.2) и полная репетиция (08). Решения — D-133…D-138, обезличенный протокол прогона — `snapshot-protocol.md`, проверки этапа — `evidence.md`, «Этап 06.1».

Код — `scripts/snapshot/`, только стандартная библиотека Python:

| Файл | Назначение |
|---|---|
| `snapshot.py` | CLI: `create`, `verify`, `list`, `delete`, `protocol` |
| `capture.py` | план (каталог схемы, проверка типов), одна транзакция выгрузки, файлы |
| `codec.py` | кодирование строк, SQL дайджеста и счётчиков, каталог схемы, литералы восстановления |
| `verify.py` | печать, строки с диска, восстановление во временную базу, полнота по картам, вложения, телефония |
| `common.py` | пути, права, блокировка, клиенты MySQL (production по ssh, стенд — `mysql_root`) |
| `remote/file_list.py` | опись файлов с sha256 (на сервере — inline через `python3 -c`, локально — по копии) |

Тест кодека на стенде (синтетика, без production) — `tests/snapshot/test_roundtrip.py`.

## Команды

```bash
task snapshot:create                     # выгрузка → staging → проверка → атомарное переименование
task snapshot:verify -- <id>             # повторная полная проверка (временная база стенда создаётся и удаляется)
task snapshot:verify -- <id> --no-restore    # быстро: печать, файлы, строки
task snapshot:list                       # снимки, незавершённые прогоны, оставшиеся временные базы
task snapshot:delete -- <id> --yes       # удалить снимок (или .staging-<id>, или vtsnap_… по журналу)
task snapshot:protocol -- <id>           # обезличенный протокол в docs/migration/snapshot-protocol.md
task test:snapshot                       # тест кодека на стенде
```

Коды выхода: `0` — проверен; `2` — копия верна источнику, но есть **находки** (расхождение с картами, отсутствующий в источнике файл) — снимок сохраняется, находки смотреть в отчёте; `1` — сбой (при `create` незавершённый снимок удаляется, журналы — в `failures/<id>/`).

Запускать от разработчика (не root). Нужны: ssh к `sergey@serv.sergeyem.ru` (`AUDIT_HOST`), `sudo -n` там и локально, работающая MySQL стенда (`task stand:health`). Каталог снимков — `SNAPSHOT_ROOT`, по умолчанию `/data/itvolga/espo-private/snapshots`; внутри Git-дерева инструмент работать отказывается.

## Состав

| Часть | Источник | Что входит | Что не входит |
|---|---|---|---|
| БД `vtiger7` | MySQL 8.4.11 на сервере | **все** 784 таблицы целиком: живые и удалённые записи, история изменений, журналы, настройки, справочники, счётчики, секреты (решение владельца 2026-10-06, D-133) | — |
| БД `asteriskcdrdb` | там же | таблица `cdr` целиком | — |
| Файлы `vtiger` | `/var/www/serv_itvolga/vtiger7` | `storage/` целиком (включая кэш MailManager и файлы без строки вложения), `test/logo`, `test/upload` | прочее в `test/` (скомпилированные шаблоны, mosaico, маркеры лицензий), `vendor/`, `cache/`, `logs/`, `user_privileges/`, `config*.php`, код (код — `scripts/audit/sync-vtiger-src.sh`) |
| Файлы `cdr-csv` | `/var/log/asterisk/cdr-csv` | каталог целиком (`Master.csv`) | — |
| Файлы `monitor` | `/var/spool/asterisk/monitor` | все записи разговоров, завершённые до границы | запись, идущая во время снимка (время изменения позже границы) |

Таблицы с секретами (хеши паролей пользователей, пароль IMAP, токены Google и webservice, ключ шлюза PBX, пароль SMTP, ключи расширений) и история значений полей доступа контактов (`vtiger_modtracker_detail` по `cf_1322`–`cf_1328`) хранятся **как есть**: защита — права каталога. Инструменты никогда не выводят значения строк, имена файлов вложений и значения полей доступа в консоль, протокол и Git: туда попадают только идентификаторы схемы, счётчики, размеры и дайджесты целых артефактов. Ошибки описи файлов называют операцию и errno, но не путь. Сообщения клиентов `mysql` и `rsync`, где могут быть значения и имена файлов, пишутся только в приватные журналы внутри снимка (`logs/`, `reports/*/logs/`, 600) и в `failures/<id>/`.

## Каталог и формат v1

```text
/data/itvolga/espo-private/snapshots/            700, владелец — разработчик
  .lock                                          flock: create/delete — исключительно, verify/list — разделяемо
  tempdbs.journal                                журнал временных баз стенда (created/dropped, точные имена)
  failures/<id>/                                 журналы и отчёты неудавшегося прогона (без данных)
  .staging-<id>/                                 только пока идёт create
  <id>/                                          id = YYYYMMDDTHHMMSS (местное время начала)
    MANIFEST.json                                контракт: формат, источник, кодек, границы, состав
    SHA256SUMS                                   sha256 всех файлов, кроме files/** и reports/**
    db/<schema>/tables.json                      по таблице: движок, колонки и классы, строк, дайджест, счётчики колонок
    db/<schema>/ddl/<table>.sql                  SHOW CREATE TABLE (из транзакции снимка)
    db/<schema>/rows/<table>.hex.gz              строки (кодек ниже), отсортированы побайтно
    db/<schema>/catalogue.fingerprint            отпечаток структуры схемы
    inventory/<part>.tsv                         relpath_hex, размер, mtime_ns источника, sha256 — по каждому файлу
    files/<part>/…                               файлы с исходными относительными путями и именами
    logs/                                        stderr клиентов (приватно)
    reports/verify-<ts>/                         вне печати: report.json, attachments.tsv, audit/ (+ maps/), logs/
```

**Печать снимка** — sha256 файла `SHA256SUMS`. Файлы частей запечатаны транзитивно: их sha256 — в описях, а описи — в `SHA256SUMS`. Поэтому имена файлов (в них бывают ФИО) в `SHA256SUMS` не попадают.

**Кодек строк `hex-tsv` v1.** Одна строка таблицы — одна строка файла; токены идут через TAB в порядке колонок. Токен — `N` (SQL NULL) или hex значения в верхнем регистре; пустая строка — пустой токен. Значение кодируется по классу колонки:

| Класс | Типы | Значение | Литерал восстановления |
|---|---|---|---|
| строка | char, varchar, *text | сырые байты в кодировке колонки (`HEX(c)`): latin1, utf8mb3, utf8mb4 без перекодирования | `_latin1 X'…'` (кодировка колонки) |
| двоичный | binary, varbinary, *blob | сырые байты | `X'…'` |
| точное число | целые, decimal, year | текст MySQL (`CAST AS CHAR`, с масштабом decimal) | без кавычек, проверка формата |
| дата и время | date, datetime, timestamp, time | текст MySQL, включая нулевые даты и доли секунды; TIMESTAMP — в UTC (`time_zone='+00:00'`) | `'…'`, проверка формата |

Прочие типы (float, double, bit, enum, set, json, пространственные), генерируемые и невидимые колонки, представления, триггеры, процедуры и события на этапе плана **отклоняются**: прежде чем расширять кодек, нужен тест туда-обратно. В источнике 2026-10-06 их нет. Строки сортируются побайтно — это детерминированно и для 268 таблиц без первичного ключа (дубли сохраняются).

**Дайджест таблицы** — четыре суммы 64-битных «полос» sha256 каждой закодированной строки; от порядка строк он не зависит. SQL (`codec.stat_sql`) и Python (`codec.lanes_of`) считают его одинаково. Вместе с ним в той же транзакции считаются `COUNT(*)` и по каждой колонке «непустых/ненулевых» — те же выражения, что у `field-map.csv` (`gen_sql.nonempty_expr`).

`DATETIME` хранится как записан: правила часовых поясов источника (D-30) применяет импорт. `TIMESTAMP` читается и восстанавливается в UTC.

## Границы согласованности

| Часть | Граница | Как обнаруживаются изменения во время снимка |
|---|---|---|
| `vtiger7` + `asteriskcdrdb`, InnoDB | **один момент T0**: одна сессия `SET SESSION TRANSACTION READ ONLY` → `START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY`, все таблицы обеих баз читаются из одного снимка MVCC | в той же транзакции сервер считает число строк и дайджест; полученные строки должны дать те же значения, иначе сбой |
| 3 таблицы MyISAM `vtiger7` (`vte_duplicate_check_merge_setting`, `vtiger_import_1`, `vtiger_spcompany_seq`; 1–3 строки) | вне снимка MVCC, читаются в окне транзакции | дайджест в начале, при выгрузке и в конце окна должен совпасть, иначе сбой (запустить снова); промежуточное изменение с возвратом не обнаруживается. Каждый `SELECT` по MyISAM берёт табличную блокировку чтения на время оператора (миллисекунды): запись в эти таблицы в это время ждёт — как при любом запросе аудита |
| Схема (DDL) | каталог (таблицы, колонки, индексы, объекты) снимается на плане, в начале и в конце транзакции | отпечатки должны совпасть, иначе сбой («schema changed», запустить снова) |
| Файлы `vtiger`, `monitor` | опись после транзакции; в снимок берутся файлы со временем изменения ≤ конца транзакции | файлы вложений пишутся один раз, поэтому каждый файл, на который ссылается строка снимка, уже есть; более новые файлы не берутся (счётчик «новее границы»); файл, меняющийся, исчезающий или нечитаемый во время описи, — повтор части (до 3 раз), затем сбой; отсутствующий настроенный путь или каталог, который не удалось прочитать, — сбой (неполная опись не принимается); sha256 копии = sha256 на сервере |
| Файлы `cdr-csv` | файлы целиком на момент описи | CSV только дописывается и может содержать звонки после T0 (их число — в проверке C10); sha256 копии = sha256 на сервере, иначе повтор |

Транзакция держит разделяемые блокировки метаданных (MDL) читаемых таблиц до `COMMIT`. Обычные записи Vtiger в таблицы InnoDB при этом не ждут (о MyISAM — строкой выше), а DDL ждал бы конца транзакции. Длительность транзакции пишется в `MANIFEST.json`. `FLUSH TABLES WITH READ LOCK`, `LOCK TABLES`, `SELECT … FOR UPDATE` и `INTO OUTFILE` не используются: сгенерированный SQL перед отправкой проверяется списком разрешённых операторов (`capture.lint`). На сервере ничего не создаётся: опись файлов передаётся inline (`python3 -c`), копирование — `rsync` со стороны сервера только отправителем (`sudo -n rsync`, `nice`/`ionice`).

## Контрольные суммы и проверка

`create` публикует снимок только после полной проверки; `verify` её повторяет:

| Код | Проверка | Итог при расхождении |
|---|---|---|
| V1 | `SHA256SUMS` сходится, лишних и недостающих файлов нет, права 700/600, ссылок нет | сбой |
| V2 | каждый файл части = опись (размер, sha256), лишних нет | сбой |
| V3 | строки с диска: формат токенов, число колонок, порядок, число строк и дайджест = значения сервера из транзакции | сбой |
| V4 | восстановление во временную базу стенда; отпечаток схемы, число строк, дайджест и счётчики колонок на копии = значения сервера. Если V1–V3 не прошли, восстановление **не выполняется**: SQL снимка исполняется от root MySQL стенда. Каждый DDL обязан быть одним оператором `CREATE TABLE` своей таблицы — посимвольный разбор: вне строковых литералов и идентификаторов нет `;`, `\` (команды клиента `mysql`) и комментариев (`/*`, `--`, `#` — `SHOW CREATE TABLE` их не выдаёт); то же проверяется при выгрузке | сбой |
| V5 | временные базы удалены по точному имени | сбой |
| C1 | каждая пара «таблица.колонка» `field-map.csv` есть в снимке | находка |
| C2 | источник каждой связи `relations.csv` есть в снимке (`таблица`, `таблица.колонка`, составное выражение распределения платежей) | находка |
| C3 | каждый модуль с записями есть в `field-map.csv` | находка |
| C4, C5 | аудит (`scripts/audit/sql`, `gen_sql.py`, `consolidate.py`, `build_maps.py`) на восстановленной копии пересобирает карты; они совпадают с картами в Git во всём, кроме счётчиков | находка: новые/исчезнувшие строки или изменённая судьба значат, что карту пора пересобрать (`task maps:build`) |
| C6 | файл каждого живого вложения есть в снимке (правила `check_attachments.py`; несколько кандидатов — «неоднозначно», а не первый попавшийся) | находка |
| C7 | принятые потери источника (D-23): фото контактов без файла, внутренние документы без вложения | сведения |
| C8 | логотип юрлица (`vtiger_organizationdetails.logoname`) есть в `test/logo` | находка |
| C9 | запись каждого `cdr.recordingpath` есть в снимке | находка |
| C10 | CDR CSV: строки, строки после T0, общие `uniqueid` с MySQL | сведения |
| C11 | `Master.csv` есть в снимке | находка |

V3 и V4 повторно кодируют восстановленные значения тем же SQL. Независимую от кодирования проверку дают счётчики колонок и тест туда-обратно на синтетике: граничные значения, latin1 0x80–0x9F, нулевые даты, TIMESTAMP, decimal, blob с 0x00, дубли без ключа, MyISAM, AUTO_INCREMENT с нулём.

Приватные результаты проверки — `reports/verify-<ts>/`:
- `report.json` — итоги и счётчики;
- `attachments.tsv` — вложение → путь в снимке → размер → sha256, нужен этапу 06.3;
- `audit/` — пересобранные карты в `audit/maps/`.

## Временная база стенда

Восстановление идёт в базу `vtsnap_<время>_<6 hex>_<схема>` на MySQL стенда (127.0.0.1:3384, root через `auth_socket`).
- Имя пишется в `tempdbs.journal` **до** `CREATE DATABASE`; удаление — `DROP DATABASE` этого точного имени, затем проверка отсутствия. Удаление по шаблону не используется.
- Все сессии стенда идут с `sql_log_bin=0`: binlog стенда включён и хранится 30 дней, без этого копия production осталась бы в журналах стенда. Общий и медленный журналы стенда выключены (проверено 2026-10-06).
- Сессия загрузки: `sql_mode` источника + `NO_AUTO_VALUE_ON_ZERO`, `time_zone='+00:00'`, `sql_generate_invisible_primary_key=0`.
- Бэкап стенда (`task stand:backup`) эти базы не включает, а `task stand:uninstall --purge` удалил бы их вместе с каталогом данных.
- Если процесс был убит, `task snapshot:list` покажет оставшуюся базу, `task snapshot:delete -- vtsnap_… --yes` удалит её (только имя из журнала).

## Права и очистка

- `umask 077` задаётся при импорте `common.py`: каталоги — 700, файлы — 600 с первого байта; корень проверяется (вне Git, владелец, 700, не ссылка).
- Снимок публикуется атомарным переименованием `.staging-<id>` → `<id>`; при сбое staging удаляется, журналы остаются в `failures/<id>/`.
- Автоматической ротации нет (решение владельца 2026-10-06). Удаление — только `task snapshot:delete -- <id> --yes`: точное имя, прямой потомок корня, не ссылка, с `MANIFEST.json`.
- Снимок содержит секреты и персональные данные. Если `/data/itvolga/espo-private` попадает в резервное копирование рабочей станции, туда попадают и снимки. После переключения (этап 11) и периода проверки снимки удаляются по решению владельца.

## Чтение снимка на следующих этапах

- Таблицы: `verify.TempDatabases` + `verify.restore_sql` загружают схему во временную базу стенда; импорт 06.2 читает её SQL-запросами и удаляет. Режим «оставить базу на время импорта» добавит 06.2. Строки можно читать и напрямую: `db/<schema>/rows/*.hex.gz` + `tables.json` (классы колонок, `codec.literal`).
- Файлы: `reports/verify-*/attachments.tsv` (вложение → путь внутри `files/vtiger/`), опись `inventory/<part>.tsv`; логотип — `files/vtiger/test/logo/<logoname>`; записи — `files/monitor/<recordingpath без /var/spool/asterisk/monitor/>`.
- Дельта (06.4): два снимка одного формата сравниваются по дайджестам таблиц (`tables.json`), затем — по строкам; нумерация (`vtiger_modentity_num`, `*_seq`) — обычные таблицы. Позиция binlog не фиксируется.

## Ограничения

- Абсолютной атомарности «база + файлы» нет: части сняты последовательно, у каждой своя граница (таблица выше).
- Отсутствие DDL доказывается совпадением отпечатков в трёх точках. Изменение схемы, вернувшееся к исходной до конца транзакции, не обнаруживается.
- Записи `monitor`, идущие во время снимка, не берутся; повторный снимок их возьмёт.
- Неизвестный тип колонки — отказ до выгрузки; расширение кодека — с тестом туда-обратно.
